# BF16 分支报错现状与修复说明

修复提交：`d49a723`。分支：`codex/oscar-bf16-attention`。main 和 stable 未修改。

## 本次问题

用户在**关闭 prefix cache**的情况下启动新的 BF16 分支，服务启动并完成多条请求后，四个 TP worker 在 2026-10-16 04:54:23 报 `507015`，底层明确提示 **Vector 读写 UB 越界**。四卡报错的 `current PC - start PC` 均为 `0x69b8`。

这是本轮 BF16 改动后出现的回归，按我引入的问题修复。日志中的 `DynamicQuantV2` 和 query rotation 是异步错误暴露位置，不能据此把责任转给原生算子或用户的 prefix cache 设置。没有要求用户重新配合真机定位。

原始日志：[target_apc_off_failure.txt](../reports/bf16_ub_fix_20261016/target_apc_off_failure.txt)。

## 定位到的具体缺陷

新增的 FP32→BF16 转换使用了大块 `Cast(..., count)`，底层走 counter-mode VCONV。静态检查没有发现张量分配容量超限，原先的 CPU-debug 也通过，但这些检查没有覆盖该转换形式的真实设备指令执行。

本地单核设备指令模拟给出了确定性线索：小块 query/padding 转换完成；大型 KV 转换已经发出却未完成，随后进程内存持续膨胀。不同资源限制下，两份 trace 停在相同指令序列，AIV0 都是4594条、末Id8351，AIV1 都是4868条、末Id8285。排除本地共享内存占用和人为虚拟地址限制后，旧转换形式仍触发异常。

关键对照是：**保持同一输入和 BF16 数学合同，只替换转换指令形式，完整算子由异常终止变为通过。** 因此，大count转换形式是本地已复现并修复的缺陷。没有目标二进制的PC映射，不能把本地结果写成已唯一证明真机 `0x69b8` 的指令归属。

## 怎么修复

新增共享实现 [`attention_bf16_cast.h`](../csrc/kernels/attention_bf16_cast.h)，将转换改为：

- normal-mask，每次最多64个FP32元素，`repeat=1`。
- 每次最多读取256B、写入128B；固定stride `{1,1,4,8}`。
- 保留 round-to-nearest-even 舍入，不改变精度容差。

q4/q1 decode 的七处新增转换、C4和C16各六处新增转换全部使用同一实现，覆盖Q、K/V、P和归一化结果的发布。两个生成器、生成源码、源指纹和探针绑定同步更新，防止下一次生成恢复有问题的大count调用。

QK/PV/Rv仍使用BF16乘数，FP32累加和softmax/LSE保持。没有退回FP32 attention、关闭MTP、开启prefix cache绕过问题，或引入完整历史BF16恢复。原INT2解包、物理缓存、事件链、ABI、冻结guard和启动参数保持不变。

## 更新启动

当前已在BF16分支时：

```bash
git pull --ff-only && bash scripts/install_serve.sh --variant candidate
```

默认仍关闭prefix cache、显式16384 token预算、原生调度器，默认0–3卡/8989；后四卡模式仍追加 `--rear-cards`。修复无需额外开关。
