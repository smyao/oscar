# BF16 decode validation

The user's later instruction cancels performance measurement. No further CAModel arm or OOM retry is authorized by this workflow. The already completed FP32 arm and incomplete BF16 arm are retained as historical receipts under `reports/bf16_decode_20261016/performance_cancelled`; they establish no BF16 speedup. The remaining acceptance work is correctness and build integration.

The user authorized this separate branch on 2026-10-16. Its numerical contract is `configs/acceptance_bf16.json` (`oscar_bf16_attention_v2`): QK, PV and final inverse-value rotation use BF16 operands and FP32 accumulation. Online maximum, sum, alpha, normalization and LSE remain FP32. INT2 storage, FP16 scale/zero and the existing error/metadata protocol remain unchanged.

`tools/generate_bf16_decode.py` pins the main `7047ce36` q4 finite-reader source. The generated source supplies q4 and q1 entrypoints. It keeps the two bounded KV buffers and all three attention sources, replaces the old FP32 NZ8 history layout with BF16 natural ND publication followed by Cube NZ16 conversion, and retains the original final-Rv synchronization. The final Rv matrix is natural BF16 ND prepared before serving, with no per-request host conversion.

P has its own 16 KiB region in the unused upper half of the former FP32 Q slot. Publishing BF16 P over the old FP32 score base would cross the two AIV row ownership ranges. All active Q/P/K/V/score/PV byte ranges are now disjoint. The allocation bound remains 1,146,880 bytes/core; effective operand DMA element size is two bytes. Cast reuses dead natural UB after the original FP32 metadata/dequant and softmax-alpha consumers, with explicit MTE3-to-Vector ownership barriers. Explicit AIV UB is 158,656 bytes, below the reserved 184 KiB limit.

`probe.cpp` runs real AscendC prepare, the complete BF16 CV including Rv, and merge through the official CPU debugger. It checks every partial and LSE element against a separately generated task oracle, all merged outputs, exact fault status checks, immutable inputs and allocation guards. `prepare-only` emits actual tasks without claiming attention numerical completion. The task oracle comes from `python -m tools.probe_bf16_attention export-reference`; original FP32 expected files remain intact.

`replay.py` adapts the existing complete CAModel runner using exact source anchors. It removes the historical FD-mutating logger and requires the official zero-dump LOG mask. Both FP32 main and BF16 candidate are compiled into one library, with unchanged cache/model settings and all task/AIC/AIV profiles required. The baseline retains its original FP32 oracle; the candidate additionally checks every BF16-contract partial and LSE. Each arm has a 600-second hard wall limit enforced externally. Timing covers CV including Rv; merge, final output copy and model serving are outside that timing scope.

Archive references: #126 preserves query/padding ownership; #145 and #154 require actual cross-pipeline ownership rather than CPU ordering assumptions; #148 prevents local timing from becoming a model-quality or end-to-end claim; #157 leaves the frozen guard and explicit discard protocol untouched. D.4's 6.5-second whole-history restoration and 209–215 ms store costs are historical failure boundaries. This reader never creates a history-sized restored tensor. Source checks, CANN compilation, CPU simulation, CAModel completion, real NPU execution, graph replay, model quality and end-to-end performance remain separate evidence states.
