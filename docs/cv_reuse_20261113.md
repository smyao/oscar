# C4 的 L1 复用与 C16 的 score 环

本轮以 `b49a689` 为基底，只处理已确认的数据重复装载和中间地址工作集。已亲读技能、启动文档 D.4 完整原始日志及档案 #145/#150/#151/#154/#164/#172。旧 D.4 的整历史恢复约6.5秒是禁止重现的失败路径，不是本轮当前耗时。

生产改动由 `tools/cluster_prefill_transform.py` 统一生成，完整母源保持原 SHA，逆变换必须恢复完整原文。两条派生源使用原 ABI 和已有 candidate 路由；没有新增长度阈值、运行开关或启动参数。正常 `start_node93_oscar.sh` 和固定 `install_serve.sh --variant candidate` 均构建同一派生源，旧构建缓存因源签名变化而失效。

## C4：每簇一次 K、一次 V 的显式 L1 装载

旧 C4 的四个成员依次调用 GM-B Matmul，执行顺序为 `QK0,QK1,PV0,QK2,PV1,QK3,PV2,PV3`。同一 KV256 的 K/V 在 Matmul 调用间没有显式驻留保证。

新实现从受保护的 C16 母源逐字复用单 B1 的 `LoadResidentB`、`MatmulResidentB`、普通 Matmul 包装和 tiling 配置。只有一个 SDK Matmul 实例，新增一个128KiB外部 B1；保留 SDK 资源静态断言 `shareL1Size + 128KiB <= 512KiB`。没有第二套 SDK 工作区，没有新增 GM 或 UB。

执行顺序为：

```text
wait KVReady → load K to B1
QK0 → QK1 → wait P0 → QK2 → wait P1 → QK3
drain P2/P3 → load V to B1 → PV0 → PV1 → PV2 → PV3 → RoundDone
```

两条 AIV 都完成 score 消费并发布 P/alpha 后，Cube 才能重用对应的两个 score 槽。P 位于每个成员自己的 Q 槽后半部，四个 FP32 状态也分别保留。切换 B1 前沿用 C16 的 `MTE1_MTE2` 屏障，载入后沿用 `MTE2_MTE1`。下一轮仍由 `RoundDone` 保护上一轮原子累加完成；KV 双缓冲预取及最终逐成员发布握手保留。

按 D256、完整四成员 KV256 计，跨成员 B 的语义 GM 装载从8份128KiB降为2份128KiB，省786,432B，即该项75%。这不是 HBM 实测减量，旧 SDK/L2 也可能命中。QK/PV 次数、每个成员 K128 累加顺序、BF16输入、FP32状态和原子输出方式均保持。

存在明确的性能取舍：PV 延后到四个 P 都就绪后，改变了与 softmax 的重叠方式；L1复用减少重复装载，但净延迟需要设备验证，不能直接推算为75%提速。普通 C1 任务的 `CubeTask`、`VectorTask` 和调用顺序未改，但其 Matmul 的 B 传输也改为相同 B1 包装，仍每次 QK/PV 各装载一次。不能声称普通路径完全没有变化。现有 C16 同形实现为接口依据，新增普通三源及短 query 验证覆盖这个风险。

## C16：16个 score 地址槽改为4槽复用

现有 Cube 在提交成员 `i>=4` 前已经等待 `PReady(i%4)`；两条 AIV 只有读完旧 score、完成 softmax 和 state 发布后才设置该旗标。因此可以把成员 `i` 的 score 地址映射到 `i%4`，无需新增或删除同步。

只改变 `SelectClusterSlots` 内的 score 地址计算。CubeCluster、VectorCluster、Softmax、SpillState、ProbabilityOffset 等完整方法被 SHA 绑定；其数学及所有权改变会使变换拒绝生成。Q/P 与 online state 仍各有16份，allocator 大小保持，避免改变图地址及其他旧布局。

每核被 score 访问的地址集合容量从2MiB降到512KiB，减少1.5MiB（75%）。每个完整历史 tile 的 score 写读合计仍为4,161,536B；此项改善的是地址复用距离，不是减少累计 DMA。不能宣称 L2 命中率已提高75%、分配容量减少或 HBM流量等量下降。

## 未加入跨簇首 tile 缓存的理由

核内现有 C4/C16 已经共享簇内解包，不能重复计算这份收益。额外设计过每核只缓存一个首 KV256、直接发布到旧 K/V 空闲半槽的方案，它不需要新增全历史缓冲或缓存复制，但需要键比较、状态及新的生命期管理。

[可复现离线模型](../reports/cv_reuse_20261113/analyze_cross_cluster.py)按当前 task owner、簇条件和路由计数。以下为 GQA6、D256、每卡2个 KV head、20个 Cube、历史32768、split=1的合成条件；不是现场分布：

| 单步 query 分布 | 现有路由 | 可省全部 source0 KV256 解包比例 |
| --- | --- | ---: |
| 1×16384 | C16 | 0.3586% |
| 8×2048 | C4 | 0.1202% |
| 4×4096 | C4 | 0.4207% |
| BS16/28，每请求 q1/q4 | decode | 0% |

首 tile 命中率的分母是簇数量，不能冒充整个历史的解包减少率；每簇有 L 个历史 tile 时，上界仅为1/L，普通历史任务还会稀释收益。虽然不新增分配，额外保留一个tile仍可增加256KiB/core活跃地址覆盖。短历史可能有更大比例，但没有证据抵销新增成本，不引入长度特判。该方案明确不进入生产，而不是将无净收益依据的缓存当作“全部优化完成”。报告保存了资源区间、不同 split/core/history 的敏感性及未验证边界。

INT2展开、必要的 AIV→GM→Cube 交接、各 query 的 QK/PV 和 FP32 online state 仍存在。没有通过全历史 BF16 恢复、跨请求混用 KV、删除错误检查或猜测 L2 hint 来消除这些必要工作。

## 验证和交付边界

最终295项主机检查通过，具体命令、各次结果与源 SHA 保存在 [validation.json](../reports/cv_reuse_20261113/validation.json)。验证包含完整源逆变换、构建缓存拒用、candidate实际路由、三 actor 控制、ND→NZ矩阵输入位、错误状态、tail、普通三源及固定地址换输入。C16穷举162,756个短轮状态、完成1,024次随机或偏置调度，并用单AIV提前放行及第二代不写新score两个负控验证检查器会拒绝错误。

首次综合运行有一项编译测试因macOS默认developer路径失效失败，显式选择已有Xcode后该项通过；原始失败JUnit保留。C4测试第一次将实际36个组合误计为54，修正计数断言后通过，没有减少用例或改动生产算法。

主机模型只证明所建模的控制和位传输，不模拟 CANN 实际浮点归约或硬件异步时序。本机没有 CANN SDK/bisheng/Lima；CANN编译、官方CPU-debug、NPU数值、图捕获/回放、模型质量和性能本轮均未验收。两个模式的真实NPU功能探针已更新，既有精度门和失败阻断保持；没有连接真机或运行测速。

PC/MemCache、MTP、PT/clip/recipe、原生调度、q1/q4 decode、timer和服务参数均未修改。该交付不能据此承诺 BS28 的吞吐或模型质量已经达标。
