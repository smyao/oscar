# Bounded shared FP32 history experiment

**Performance correction:** the grid20 C4 subset had one attention-owning Cube (AIC3), while the new consumer used four (AIC12–15). Its 3.595× span ratio is therefore confounded by parallelism and cannot establish shared-decoding throughput or enter a saturated prefill/whole-run budget. Active AIC duration sums were nearly equal (2,154,251 vs 2,149,658 ticks); new active AIV durations plus producer were 4,845,359 vs old 4,386,648 ticks, about 10.46% higher. These actor durations include waits, so they are not pure operation counts. See `reports/shared_fp32_owner_audit_20260930.json`. The combined grid1 attempt exhausted its unchanged 600-second process limit; the same candidate then completed in a separate 600-second process without rerunning baseline. Its full producer+consumer span was 2,948,302 versus the previously completed grid1 C4 baseline 3,230,822 ticks (about 8.74% lower, 1.096x). This sparse-pipeline comparison still includes empty-task and cluster-scan differences and does not isolate shared-mechanism gain or support a whole-run budget.

Archive #126/#129/#145/#148–155 and startup Appendix D.4. This standalone project does not register or select a production operator. It supports source0 for one dense request, D256, Hq6/Hkv1, S1 and the existing query tile of 21 tokens. Padding holes, multiple requests, extra KV heads and other split policies require a separate implementation and validation.

The producer reads striped INT2 once into one at-most-8192-row rotated FP32 K/V buffer. It preserves stored FP16 metadata and FP32 multiply then add. The consumer retains the fe0 QK, KV256 softmax/PV recurrence, masks, per-lane status and final Rv transpose. Complete KV256 matrices go directly from shared GM to Cube. Each original task's incomplete last KV256 gets a private copy with zeros beyond its original `kvend`, so pre-mask checks and zero-times-NaN behavior retain the original domain. Producer row errors are consumed only within that task's original per-lane rows.

Raw FP32 accumulator, maximum and sum remain in UB within each 8K tile. Only these raw states and the error code are saved at the boundary; normalization and Rv transpose happen once after the last history tile. Query values reload on a new launch, but their original finite check executes only on the first block so a carried metadata error cannot be overwritten. Producer, consumer and next producer must use one ordered stream. The shared K/V capacity is 16 MiB plus a 32 KiB row-status buffer, independent of context length; per-query state grows with the number of query groups. No whole-history inverse rotation or BF16 restore is used.

D.4 comparison: this is the history expansion/FIA phase. The historical full restore cost 6499.8–6655.1 ms/card while FIA was about 18.7 ms. Sharing a bounded block removes repeated expansion and publication across query groups, while adding producer launches, query reloads and occasional state copies. Those structural changes do not establish target latency. Source0 performance must compare the sum of producer and all consumer work against the current striped C4/C16 route selected for the same shape; fe0 is only a numerical reference.

`tools/experiments/export_shared_fp32.py` exports deterministic CPU goldens. `probe_consumer.cpp` compares the actual fe0 AscendC implementation byte for byte and checks an independent dense source0 oracle with frozen 0.005 absolute/relative tolerance. It covers q21/context511, q385/context511, q21/context8513 across two 8K tiles, a future-only NaN, a visible NaN, and a carried-error-order construction (finite large Q whose reduction overflows, zero K, first-block V scale zero). Error cases compare the original failure bytes and do not claim a finite oracle output.

Configure with `ASCEND_HOME_PATH`, `SOC_VERSION=ascend910b4`, and `OSCAR_SHARED_FP32_CPU_DEBUG=ON` for official tikicpulib CPU execution. Without the CPU flag, CMake builds a CANN library including the current striped C4 denominator. Put CANN `tools/bisheng_compiler/bin` in PATH before a clean build. `tools/experiments/replay_shared_fp32.py` runs direct ACL on local CAModel, preserving small task-cycle profiles and redirecting only its own dump files. An explicit `--query-starts` records a task subset in its result and cannot establish full-shape performance.

Evidence is in `reports/shared_fp32_experiment_20260930.json`. CANN compilation and official CPU results are separate from CAModel cycles, target NPU execution, graph replay, model quality and the eight-minute whole-run target. None of those latter gates is implied by the CPU results.

Final local evidence on 2026-09-30: all seven official CPU-debug invocations passed (six distinct cases; q385/context511 was repeated after the scope/error-order audit). The final shared library also completed a local CAModel comparison against the **current striped C4** on the explicitly selected query leaders 252/273/294/315 from the q385/context511 fixture. One C4 cluster was activated; all partial/LSE/status bytes matched and the selected source0 independent oracle passed. C4 took 2,193,992 model task ticks. Producer 28,611 plus consumer 581,648 totaled 610,259 ticks; their same-stream start-to-end span was 610,268 ticks. This small source0 task subset is a correctness/scheduling result, not complete q385, >8K-context CAModel performance, or a whole-model speedup. The full q385 initial simulation exhausted its configured 600-second limit after completing fe0 and producer; no whole-candidate ratio exists for that attempt. The completed subset model's host wall log contains an unexplained clock/runtime discrepancy, so only preserved model cycle counters are used here.

The matched-grid attempt used the exact same task bytes (SHA256 `8dff25a44419924b0c5af2b7d80a256b37ab528cf05832e0f7f575b87665bdd7`), both CV arms at one Cube and producer at one AIV. It completed current C4 (3,230,822 model ticks) and producer (160,744 ticks), then hit the original 600-second overall limit while consumer was uncompleted. No numerical outputs or complete candidate span were retrieved. Budget exhaustion versus a consumer stall remains unresolved; no definite new flag/ownership defect was found in the source audit. No deadline increase or baseline rerun was used; the necessary bounded candidate-only continuation is recorded below. The sparse task table also makes old C4 publish 1540 additional empty status words and perform 385 additional task reads in its cluster pass, so even a completed result would include scheduling overhead. A complete service comparison must additionally include nonhistory CV costs.

The candidate-only continuation retained the same library, all input hashes, selected task bytes and grid1 configuration. It completed in 341.503 seconds under the same 600-second limit: producer 158,212 plus consumer 2,789,747 gave 2,947,959 task ticks; the same-stream span was 2,948,302 ticks, including the diagnostic gap between stages. Each stage was immediately copied to host and saved with a checksum manifest. All candidate output/LSE/status bytes matched previously saved grid20 C4 output on the identical input; the independent frozen oracle passed (max output 1.073e-6, LSE 9.537e-7). The prior grid1 baseline output was not saved, so direct grid1-old/new numerical parity remains unverified. Compressed stage data and manifests are preserved in reports/shared_fp32_camodel_evidence_20260930/. This work remains an isolated prototype and is not integrated into production.
