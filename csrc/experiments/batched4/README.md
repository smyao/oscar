# M512 batched C4 candidate

Archive #126/#129/#145/#148–153 and startup D.4 govern this candidate. Both install_serve.sh and install_observe_serve.sh enable its production binding through the shared --variant candidate preset. Observation runs the batched-history NPU gate before serving; direct installation provides no acceptance evidence. The original fast C4 kernel is unchanged.

For four source0 query groups with identical request, head, split, context, and history interval, the prototype keeps one INT2 KV256 unpack. It packs four padded 128-row Q tiles into M512, calls the CANN FP32 Matmul API once for QK, computes each group's existing masked 32-row SoftmaxFlashV2 in order, then calls Matmul once for PV. Each query's FP32 online max/sum, alpha, accumulator update, final rotation, LSE, and status remain separate. Inactive P rows are explicitly zero before the M512 PV call. Other tasks run the inherited C1 path.

The alpha generated by V2 is copied as FP32 bytes to fixed per-core workspace. After PV, Vector reloads the original accumulator and updated stats, applies the saved alpha with the same Brcb/Mul sequence, then adds that group's PV result and saves one updated accumulator. This changes when independent `old_acc * alpha` runs, while keeping its order before `+ PV`; it does not introduce a second accumulator spill. The M512 Matmul tiling can still change FP32 result bits, so same-input old-C4 bitwise and frozen-oracle gates are mandatory.

At D256 the fixed workspace is 2,627,584 bytes/core, compared with 1,839,104 bytes/core for fast C4. It never scales with history length. The larger score/P matrix holds 4 × 128 × 256 FP32 values. The CPU-debug target uses the actual AscendC kernels and the existing independent golden files; simulator success cannot establish NPU precision, graph replay, model quality, or device speed.

Independent CANN build (VM only):

```bash
cmake -S csrc/experiments/batched4 -B build/batched4-device -DSOC_VERSION=ascend910b4 -DASCEND_HOME_PATH=/usr/local/Ascend/cann-9.1.0
cmake --build build/batched4-device -j2
```

The full D256 q336 active-cluster fixture uses two fresh official CPU-debug
processes, each with the existing 120-second cap. The first runs old C4,
checks its independent oracle, and saves the exact output bytes. The second
loads those bytes, runs batched4, compares partial/LSE/status/stats and checks
the same oracle. Input and artifact hashes are checked before and after:

```bash
python3 -m tools.run_batched4_cpu_debug \
  --executable build/batched4-cpu/oscar_batched4_cpu \
  --fixture reports/vm-cv-mixed-balanced/goldens/c16_d256_q336_c65 \
  --mode old_only --output reports/batched4-d256-cpu.json \
  --log-dir logs/batched4-d256-cpu --artifact-root reports/batched4-cpu-artifacts
```

The full D.4 record shows a failed all-history restore at 6,499.8–6,655.1 ms/card, separate host preparation around 725 ms and stores around 209 ms, while native FIA itself was 18.5–18.9 ms. This kernel only changes fused FIA's bounded query/KV schedule. It cannot fix host preparation or store phases and must not be credited with their time. At the current reported 64K workload, the 55 minute to roughly 7.3 minute target requires about 7.57× total speed; the 16 minute to 8 minute LongBench target requires 2×. API call reduction alone provides neither result.
