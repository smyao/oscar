# OSCAR 量化优化闭环

## 本轮覆盖规则（用户2026-10-15）

以 stable `f96820f1` 的全部已工作机制和默认启动方式为主分支基底，冻结完整 vLLM argv：默认 APC 关闭、显式预算16384、原生调度器，保留显式APC开关。下方旧默认APC开启/省略预算/120请求2–4倍要求被本条覆盖。本轮32K与64K均为300请求、512输出，目标同参原生端到端性能提升超过30%；证据见 `reports/stable_32k_64k_20261015/analysis.md`。禁止任何方式使用真机；独立完成必要本地实现/编译/模拟并交付一键入口，由用户最后认证。局部算子倍数不能冒充整轮目标，启动参数不能作为优化变量。

用户随后接纳stable→B1完整1.2256808倍（单KV CV核范围）作为新主分支基底；pipeline→B1仅1.0410662倍不再构成剔除理由。下方历史单项1.15硬门被覆盖：允许小而真实的净收益累积，但须完整路径不退化、精度/协议不放宽、资源开销显式、在最新基底去重。旧实验原门与失败记录保留，不倒改历史。最终目标仍是同参native的32K和64K端到端超过30%，不能把局部22.6%相加成该目标。完成后推主分支供用户验证，stable由用户验证后更新。

## 第一指示：找到并消除抵消 batch 收益的主要成本

**用户明确指定的第一指示：OSCAR 已能容纳更多请求，为什么吞吐没有随之提高，反而更慢？必须先找出当前 OSCAR 执行路径中抵消这一容量收益的主要成本，再围绕它组合优化，直到有依据支持既定目标。** 后续分析、实现、probe 和交付都围绕此问题展开。

1. 分开容量收益与执行成本：用实际参与 decode 的 `B`、每请求每轮有效输出 `a` 和包含 MTP 的 `T_step` 判断 `throughput=B*a/T_step`。若 batch 增长同时使 step 时间增长得更多，容量压缩尚未转化为吞吐；Running/驻留峰值只能作线索。
2. 从当前源码和已有实测追查这条断开的因果链。优先检查 INT2 读取后重建 FP32 K/V 的量、GM/L2/HBM 搬运、FP32 Cube/Vector 工作、跨管道等待，以及 MTP 为每个有效输出增加的工作。必须证明这些成本仍在当前实际路由，并区分已测热点与尚待确认的嫌疑；不预设某一项必然解释全部分钟差。
3. 先建立完整 decode/混合 step 的成本闭环，再挑改法：既看相同实际 batch 下 OSCAR 增加了什么，也看容量释放后更大 batch 是否降低了每个有效输出的成本。保留原生模型/GDN/MTP、prefill供给、爬坡与排空；不能只量局部 helper、只看存储字节或仅用两个总时长拟合原因。
4. 每个候选必须回答：**针对哪个已确认的主要成本；可减少多少实际工作/暴露等待；新增什么成本；组合后是否足以恢复 batch 吞吐收益。** 减少指令、burst 或搬运次数本身不等于净提速；完整结果不支持时保存证据并换方向，不持续堆叠小改动或扩大复杂协议。
5. 正常工作目标是让压缩节省的访存与容量发挥作用，避免反量化、浮点展开、MTP或同步成为新的限制。访存受限必须按资源层级取证；GM地址流量不能直接当HBM流量，也不能靠增加无用访问把算子变成访存受限。
6. 保持冻结精度和两个一键入口。数学改动必须与项目真正的完整原空间 oracle 对照；旋转域局部差异、CPU归约树差异不能冒充完整算子或真NPU精度失败。局部提速不得替代整轮目标；证据不足则继续定位这个主要成本，不以整理文档或一个小优化结束任务。

当前事实、字节账和未解决归因见 `docs/quant_dequant_roofline_20261011.md` 的“容量收益为何没有变成吞吐”节；该专项始终服从本总 MD。

5. **本轮明确以组合方式提速**：量化写入、反量化/布局/复用、OSCAR缓存容量与任务执行效率协同减少完整路径成本。每项须有明确净贡献或必要依赖关系，过小单项不加入；最后验证实际组合，不能拼乘各自倍率。

## Prefix caching 是必需兼容项（2026-10-12）

OSCAR 必须兼容原生 prefix caching，纳入同一优化与交付闭环。 **用户随后明确要求所有服务启动入口默认显式开启 prefix caching**：配置缺省和固定 candidate 命令都传入 `--enable-prefix-caching`，启动摘要为 `prefix_caching=true`；不得只依赖原生默认或要求用户额外加参数。用户已报告启用时报错，尚未给出错误栈；先从当前源码核实并实施，不索要该错误作为开工条件，不把推断写成该次真机根因。

- 保留原生命中/hash/引用计数/驱逐语义与 GDN 状态管理；外部插件负责使 OSCAR 的 INT2、量化元数据、精确 sink/recent 窗口及 MTP 位置在同一前缀边界一致。不能以禁用 caching、全历史恢复或绕过 OSCAR 宣称兼容。
- 核对完整/部分命中、共享前缀后分叉写入、物理页复用、抢占恢复和 reset。私有窗口或快照不得只按请求 ID、token 长度或复用过的块号认作有效；绑定真实缓存所有权/代际，避免覆盖仍被其他请求引用的状态。
- 必要验证覆盖命中与无命中的输出对照、分叉隔离、释放后复用及 graph 固定地址换元数据；MTP 和 native GDN 接缝纳入测试。主机生命周期测试、NPU/graph、模型质量与性能分别记账。
- 性能比较注明两侧 prefix caching 状态、命中 token 数与新增快照/恢复成本。命中导致少做 prefill 不能计作量化内核提速；兼容修复也不能以显存膨胀抵消 FULL KV 目标。
- 实现和证据归入 `docs/prefix_caching_compatibility.md` 与统一台账；两个 candidate 一键入口实际接入。该专项服从本总 MD，不另立性能目标。

## 从现存问题推到有价值的方案

### 并行执行与 token 效率（用户 2026-10-13）

- 原故障修复与性能组合同时推进，主代理负责资源、交叉审查、统一入口与即时交付；候选分别指派明确负责人，不能把“已交准备材料”说成“仍在执行”。并发按工具真实上限安排，满额时明确谁排队或由主代理承接，不虚报活跃子代理数。
- 每路固定当前母源、一个可证伪假设、完整路径收益门和下一决定性动作。达到门才集成；失败保存首错和真实状态，解释后切换，不堆小改动。兼容修复不等性能实验结束才推送，两入口同步。
- 复用已有精度、编译和完整配对；续跑先读该任务的完成回执，不重跑已完成实验。档案按相关标题读取，长 JSON 只提取所需字段，原始大 trace 留文件，不刷屏或反复塞入上下文。
- 源码分析/实现可并行；同一 VM 周期测量使用独占锁。子代理报告仅给新增事实、改动范围、结果、下一命令或阻塞；无新增信息不反复发送长摘要。
- 只做覆盖实际改动风险的验证；不以全量测试、无关 Git/stat 对齐或重复写长报告代替实现。运行前一次核对官方 CANN 环境与输出位置，源树/小容量 tmpfs 不承接大量调试日志。
- 用户不再提供真机反馈；独立完成所有可做的本地原生接缝、CPU-debug、编译、模拟和图契约工作。不得把缺少真机反馈当作停止理由，也不得将本地证据写成真机“100%修复”或整轮达标。

每轮先形成一个可被证伪的判断，而非看到一处低效就修改：

- 画清实际调用/所有权：target、首draft、后续draft、q1/q4/C4、source0/1/2、原生current抑制和graph/eager路由。相同位置不等于相同KV，不假设跨层/target-draft能共享数值。
- 分开输入工作量、固定成本、重复计算/搬运、真正依赖等待。只用闭合且任务计数吻合的相位；actor时长、嵌套父子时间不能相加成wall，所有wait也不都是可省成本。
- 以当前优化基底评估**新增净贡献**：完整算子/关键核变化、调用频度、当前瓶颈、额外GM/UB/同步/维护成本。阶段串行可用Amdahl条件式；流水须用依赖DAG与资源约束，不能混算。
- 不乘不相关局部倍率，不将FULL字节比、running数量或理想并行度换成吞吐。helper倍率只是helper范围；布局微测若host预pack免费，必须另扣实际publisher成本。
- **64K decode的主要机制按roofline核算**：INT2减少实际访存并释放KV容量，允许更大的实际decode批次；按用户提出的原生访存受限前提设计，要求OSCAR量化/反量化、临时数据搬运和MTP工作没有将组合推成计算或同步瓶颈。分别核算HBM/L2流量、Cube/Vector计算及关键依赖；容量增长不自动等于有效batch增长，驻留/Running也不等于当步decode batch。稳态条件下用 `X=(B_oscar/B_native)*(有效输出/请求/步_oscar÷有效输出/请求/步_native)*(T_step_native/T_step_oscar)` 估算decode吞吐比，并列MTP接受率、调度与屋顶测量的不确定性。目标的访存受限状态必须取证，不能凭压缩比宣称已实现；完整机制与边界见项目 `docs/quant_dequant_roofline_20261011.md`。
- 用已有native/OSCAR日志与真实工作量约束校准后冻结仿真；候选只改变源码证实的成本/任务量/依赖，不反调参数追目标。MTP轮数与native chunk数按证据或区间推算，不能用HTTP200或prompt吞吐为0判断完成/纯decode。
- 不机械丢弃所有小正收益，也不机械堆叠凑目标。用户当前门为**单项至少1.15倍**；达到此门且精度/协议合格的可组合，低于门的保留证据及重开条件。已测基底之间有重叠时去重计账；必要依赖可保留但不单领倍率。

需要新实验时才读技能内 [实验卡](references/experiment-template.md)，把问题、方案、预先声明的门和最终结果放进同一小记录；已有报告满足字段时直接引用，不另造重复长文档。

## 有依据地实现和验证

1. 新结构先独立research；固定唯一当前母源、ABI和数学顺序，生成派生源时保留逆向身份检查。每个CANN核按D.4四问说明对应相位、旧失败、本方案如何避免、成本边界；不把旧6500ms当作当前占比。
2. 先核UB/L1/L0/GM活跃期、真实任务归属、尾行与padding、错误优先级、cache格式及跨pipe事件。当前SDK语义拿不准先查定义与已有失败；例如TPipe保留事件、LEFT/RIGHT FMATRIX不能凭API名字猜。临时绕错不能掩盖协议缺口。
3. 只做决定性验证：源/ABI→独立oracle与应保持的逐位域→完整算子配对→实际路由/设备/graph接缝。选覆盖改动风险的有效值、nonfinite、错误域、尾部、跨请求/跨轮与固定地址改输入，不机械扩大矩阵或镜像测试。
4. CPU-debug、CANN编译、CAModel、真实NPU完成、graph捕获/回放、模型质量、整轮性能分栏。CPU过不替代NPU；编译、health或HTTP200不替代完成。部分trace只支持已闭合子范围，不能放行整trace门。
5. 本机Lima仅在会话授权范围内使用。沿用 `tools/experiments/run_camodel_arm.py` 的独占锁、本地文件日志和真实completion/control；实验预声明有界deadline，不擅自延长或定时重跑。中断后先核owned进程与产物，orphan/无完成输出不能采ticks。
6. 发现数值/协议错误先定位修复；已测变慢需解释具体方案为何失败。若只是局部正收益不足，记录当前是否组合及理由，再找剩余结构瓶颈，不粉饰目标达成。

每轮组合后重算剩余时间与目标差距：关键证据不足就补最有区分力的证据；可信估算仍不达标就返回剩余OSCAR主成本继续迭代；估算支持目标且本地必要门通过时，按已有授权交付用户做最终真机认证。明确区分“可交付待认证”和“真机验收通过”，不把无法提前取得的用户端证据变成停在原地的理由。
