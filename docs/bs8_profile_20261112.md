# BS8 用户算子统计：C4/C16 是本轮优先热点

2026-11-12 用户回传的 Device 4 统计。用户确认两侧是同一批 11 条请求、32K 输入、50 输出、最大 BS8、端到端完成，且均设置 `num_speculative_tokens=3`。本轮没有连接真机或运行新的性能实验。遵循档案 #150/#151/#152 对“完整 step、kernel 总和、局部 actor 时间”分开计账的要求，以及 #172 不以短输入退化换取单场景收益的约束；不新增真机故障编号。

原始九列表格见 [OSCAR](../reports/bs8_profile_20261112/oscar.tsv) 和 [base](../reports/bs8_profile_20261112/base.tsv)，逐项汇总、输入哈希与当前代码绑定见 [comparison.json](../reports/bs8_profile_20261112/comparison.json)。OSCAR 表来自用户附件，保留全部 93 行，去掉最后一行中文说明；base 的 74 行从用户消息转录，未修改其数值。两表 Count、Total、Avg 在原始打印的 0.001us 分辨率内一致。

**C4+C16 合计 13.782876 秒，占全部 OSCAR CV 时间的 90.613%，占所有 `oscar_*` 时间的 79.207%。** 它们只有 374 次，占 CV 总调用 1488 次的 25.134%。相比之下，decode 家族仅占全表 3.257%，store 1.062%、prepare 0.262%。因此本次已有实测支持优先检查 C4/C16 内部的历史/当前 tile 处理，不能继续以少量 padding、字段读取或日志改动作为主要性能方案。上轮这些优化的正确性和工作量证据保留，但不能把它们说成本次主要热点已经解决。

## 和当前源码的对应关系

`oscar_ascend/ops/cv_dispatch.py::select_cv_op` 保留当前 dispatch：明确的 later-draft q1 独立选路；满足 q<=4 的主模型 query 选 q4；较长 query 根据现有规则选择 C4/C16。C16 当前入口要求 `max_query_len>=8192`，不是根据历史 context 长度选版本；C4 还保留不能组成共享簇时的 C1 计算。这里只解释已存在的路由，不新增阈值，也不把 C4/C16 标签等同于每个任务都成功复用。

因此 C4/C16 的 31.437% 全表累计说明长 query / 混合 prefill 算子族值得优先优化，不能由“纯 decode step 比例高”将其忽略。step 次数比例与耗时比例是不同分母；普通 decode kernel 也可能处理短续块，名称不足以还原每次调度阶段。

OSCAR 的 CV 总调用为 1488 次，与 merge 的 1488 次一致；再加 FIA 的 170 次为 1658 次，与 store/copy-query 的 1658 次一致。这与当前 `impl.py` 中已证明单来源 current suffix 可调用 FIA、历史分支走完整 CV 的结构相符，不能据 FIA 尚存在指责它是静默回退。该算术对应仍不是单次调用的时间线证明。

同样，base FIA 的 2176 次与 OSCAR C4/C16 的 374 次不是配对 shape：不能用 60.81ms/1.19ms 的平均值直接声称 C16 比原生慢 51 倍。`_25`、`_8` 等 kernel 名称后缀保留原样，未经 launch/trace 绑定不擅自标成图阶段或某一新实现版本。当前已知 Device 4 只是此次表格的设备号，不改默认部署设备。

采集所用的 OSCAR 提交号、实际完整 argv、PC 命中 token 数、profile 起止及端到端 wall time 尚不在表中。新旧派生实现沿用同一 public ABI/kernel 名称，不能靠该表证明上一轮 `140190a` 已部署。可以依据已观测的 C4/C16 热点继续源码优化，但新实现的净收益、设备精度和图回放仍要与本次分析结论分别记账。

## 本轮实际改造

基底 `140190ac92742e7cc5d8fdc12a8372fc833718fa`，分支 `oscar-new-7`。仅处理 C4/C16 内的重复有限性检查；profile 没有拆出该子相位时间，不能将整个 13.78 秒都记作可消除开销。

| 位置 | 原实现 | 新实现及边界 |
| --- | --- | --- |
| C4 `Softmax` 完整可见的 history/window/current tile | 每行重建可见区间、归约并等待标量结果 | 复用当前 C16 已有的完整可见条件和 finite helper；普通完整块的32行检查变为一次块证书。对角线、尾部、空行保留原逐行代码 |
| C4/C16 `LoadPrecise(kind==2)` | 对最多16行 current K/V 逐行归约并等待 | Cast完成后复用已无读者的BF16 staging；普通完整块的16次检查变为一次块证书，少于8行沿用逐行判定 |

证书对工作副本取绝对值并归约。当有限的非负总和不超过 `2^110` 时，原256项行归约的任何加法中间值都远离FP32溢出上限，可确定原finite判定为真。NaN/Inf、极大值、溢出和抵消未获证时，仍执行既有A2 count-mode `vcadd/ACC_VAL` 行判定。它不裁剪或更改K/V，不把异常当作有效输入。新增Abs与块归约也有成本，减少的等待次数不是内核或端到端加速倍数。

current的 `naturalBuf` 原容量17,408 B，证书最多使用16,384 B；`scratchBuf` 原容量1,024 B，结果槽最多使用512 B。C4 Softmax复用原32,768 B `dequantBuf` 和1,024 B `naturalBuf` 结果槽。没有新增UB、L1、GM、workspace或kernel launch。current的 `MTE2→Cast→PIPE_V` 之后才复用输入暂存，helper的 `V_S` 完成后才交给原 `PublishKv`；score/P的 `MTE3→MTE2`、跨核flag和原Cast原样保留。

INT2编解码、BF16舍入、FP32 online softmax/max/sum/alpha、LSE合并、旋转/PT/clip、recent/sink、PC/MemCache、GDN/MTP、调度和启动参数均未改。q1/q4及上轮store优化也未改。采用 `attention_cv_official_cluster4_active.cpp`、`attention_cv_official_cluster16_active.cpp` 两份同ABI派生源，完整冻结母源保留。`cluster_prefill_transform.py` 绑定母源SHA，组合变换后精确逆转验证整文件。CMake编译派生源，构建前检查阻止旧二进制复用，原candidate和node93入口自动使用新产物，无需新增参数。

按档案#145/#154的DMA/流水失效教训，本轮没有更改C4的QK/PV交错顺序或引入resident-B重排，也没有修改C16的spill/restore所有权。这些路径仍有潜在成本，但缺少当前同形设备完成与净收益证据，不能据聚合表直接删屏障或重排流水。

## D.4 对照与验收

1. 对应有界融合attention内的finite检查，不是旧独立全历史解压相位。
2. D.4的6499.8–6655.1ms全历史恢复及209–215ms store是禁止重现的历史结构，不当作本轮耗时。
3. 复用tile内死缓冲，保留#145 score/P生命周期、#154跨核协议、#164有界转换和#172短输入保护；不新增输入长度阈值，不改原query-shape路由。
4. 每个获证块新增一次Abs/归约，减少逐行标量等待；聚合表不能给出获证块精确频数或设备净收益，尚无新内核端到端加速结论。

算子/生成/构建/入口/探针专项 **169项通过**。真实C++ Softmax控制代码及finite helper的主机记录环境覆盖 **2,016组**；current旧新finite代码覆盖 **4,644组、两种主机归约次序**，包含NaN/Inf、极值、抵消、±0、subnormal、旧error、尾部和scratch canary。独立可见性枚举核对逐query/head/column的原遮罩语义。数值实现、fence、ABI和母源完整身份经源比较保护；主机记录环境不模拟CANN真实算术树或异步DMA。

扩展检查 **121项通过、2项既存失败**：旧aligned-only runtime fixture使用 `fp32_metadata` 却未启用official合同，在独立 `140190a` 快照中复现相同两项失败；未改生产策略或放宽断言掩盖。初次专项中一项C++编译器路径错误，指定本机已有Xcode `DEVELOPER_DIR` 后通过。详情和原失败日志见 [validation.json](../reports/bs8_profile_20261112/validation.json)。两组通过数有重叠，不相加当作独立测试数。

真实NPU功能探针保留独立v4 oracle、poison和固定地址改输入的graph/eager逐位比较，增加C4的336 query / 641 context / 320 recent用例，覆盖完整窗口、完整current及后续尾块/对角线，两种dequant mode均纳入凭证校验。**本轮未执行设备测试**。

本机无CANN SDK/Lima；本轮CANN编译、官方CPU-debug、NPU、硬件graph、模型质量和性能均未运行。直接 `vcadd/ACC_VAL` helper沿用原A2 `__NPU_ARCH__==2201` 限制，不扩大硬件支持范围。用户同步并重新编译部署后才能产生新版本证据；不能据主机结果宣称BS28已有吞吐收益。
